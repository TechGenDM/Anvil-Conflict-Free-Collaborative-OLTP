1. OR-Set for Row Membership — Overcomplicated, Not Required
Notion Plan says: Use OR-Set with "dots" (peer_id, seq) for row existence.

Bench reality: The bench never checks OR-Set semantics directly. It only checks:

Is the row in snapshot_state or not?
Does the hash match?
What you actually need: A simple tombstone: bool flag on each row. When deleted → tombstone = True. Never physically remove from dict. In snapshot_state, skip tombstoned rows. That's it. OR-Set is a valid theoretical model but adds implementation complexity you don't need in 12 hours.

2. Cell-Level Merge — Notion Plan's Approach Has a Bug
Notion Plan says: Multi-Value Register, keep all concurrent values in conflicts list, winner_value() sorts by string.

Bench reality: assert_cell_level_merge checks:

python
Copy
u1.get("name") == "Alice Cooper"   # A's update
u1.get("email") == "alice@ex.org"  # B's update
The actual problem: u1 is tombstoned (C deleted it). So assert_cell_level_merge passes vacuously — the bench code literally says "u1 absent (cascade) — vacuously preserved" for tombstone policy. Cell-level merge matters for randomized seeds where rows aren't deleted. For those, LWW with deterministic tiebreak (compare peer_id lexicographically) is sufficient and simpler than MVR.

Fix: Use simple LWW per cell. Store (value, clock_dict) per cell. On merge, compare clocks. If concurrent, pick winner by min(peer_id). No conflicts list needed.
